# 冷读

写稿的人知道每句话要做什么，读不出不说破的地方是否落空：读者没接住时，正文里看不出任何毛病。所以要请只拿到正文的人来读，看他们自己复述出了什么。这部稿子大量靠不说破（休书不出“休”字、应亲不说为谁、撒手不说缘由），冷读专测这一层，也顺带看节奏、声口和硬伤。

不说破的地方多半铺垫在前、落点在几回以后（86 回哭、95 回不哭；89 回“因为它薄”、99 回交书）。只读到落点的人没见过铺垫，报“没接住”是必然的；照这样的意见在落点补一句点明，稿子就一路往说破上走。所以判接没接住，只请从头读起的人。

读者的意见是给作者看的笔记。本技能只读不改：不动正文、卡、骨架，不调证据等级，不打分、不计“通过”。

## 一、定范围和人手

用户给回次范围，没给就是 81–100。

- **全读（判接住，必有）：** 两位，各自独立，从引子一口气读到范围末回；范围不从 81 起的，也从 81 读起，汇总只对照范围内的落点。引子用前八十回第八十回 `refs/front80/ch080.md`。两人都说到的才算信号，一人说的只记着。读到一百回是二十一个文件，比上一轮连读（十六个）长；后几回若复述明显变短、不再引原文，写进局限。
- **分段读（看局部，可选）：** 用户要更细的读感时加。每五回一段，每段一位，先读前一回作引子。只看这几回本身：闷不闷、声口、今词、硬伤。提示里说明前文没读到；他们说“没看懂”的，汇总时单列为“可能前文交代过”，不进接住表。局部的毛病，全读两位加分段那位，两位以上说到的算信号。
- **只读一两回**（比如改完一回看读得怎样）：两位，各读前一回加这一两回，只看局部读感，不判接住。改的若是接前文的不说破处，要测就请全读。

开工前一句话告诉用户人数和大概用量：全读一位读到一百回约三十万 token（照上一轮连读推算，没实测），读到九十回约二十万；分段一位读五回约十二到十五万。

## 二、备文本

把要读的回（连引子）复制到 scratchpad 下一个新文件夹，文件名只用三位回次（`080.md`、`081.md`……），内容照 `book/` 原样。不放在仓库里，读者够不着 `bible/`、`notes/` 才是冷读。

复制完 grep 一遍，文件里不能有路径、哈希、工具名（AGENTS.md：发给模型的上下文不含哈希和文件路径）。提示里也只出现这一个文件夹的路径，读者要靠它打开文件；仓库路径、提交号一概不进提示。记下当时的提交号；汇总前比对一次，读者读的若不是现行稿，要在笔记里写明。

## 三、发读者

所有读者在同一条消息里一齐发出，后台跑。子 agent 用 general-purpose，model 填父会话的模型（AGENTS.md 的规定）。

提示照 `references/reader-prompt.md` 的模板填，全读和分段各一种。几条要紧的，改模板时别丢：

- **先复述，后评。** 用自己的话说每回发生了什么、人物为什么这样做。复述是本技能最有用的东西：拿它同本意对照，才知道接住没有。全读的还要注明哪处读到第几回才懂，“晚接住”靠这个。
- **不提示那几处不说破的地方。** 提前问“凤姐是不是被休了”，读者就会特意去找，测不出真读者的样子。要追问，等报告回来再用 SendMessage 问，且只问复述里看不出的。
- **只读列出的文件。** 不列目录、不搜索、不上网。
- **不替作者圆场，不必客气，不核脂批、不比程高本。** 要的是读感，不是考证。
- **全读四千字以内，分段两千字以内，引原文每处不超过二十字，只回报告不写文件。** 报告要能装进汇总者的上下文。

## 四、收报告

每份报告一到，就把要点存进 scratchpad 的 `reports/`（全读的叫甲、乙，分段的按段落命名），会话被压缩以后还找得回来。报告没齐不要汇总，也不要向用户预报结果。

## 五、对照本意

报告齐了，先从 `bible/skeleton.md`（回目表、情节链、已定各条）和对应的大纲卡里，列出这几回里不说破、靠读者自己领会的地方，每处写明铺垫在哪回、落点在哪回（铺垫在前八十回的，读者都读过）。再逐处看全读两位的复述：

- **接住**：读者自己说出了本意；
- **晚接住**：读到后几回才明白（注明到哪一回）；
- **没接住**：复述里没有，或读成了别的（照录读者怎么读的）；
- **读者当成了漏洞**：有意留白的地方被读成伏笔没收（如证据表的开放项）。

读者都没提的，也是结果，照记。只算读者自己说出来的，不替他们补。分段读者没读到铺垫，不进这张表。

## 六、核事实

读者报的硬伤（时序倒流、指代不清、今词、断句、东西前后对不上）逐条对正文 grep 核过再写，读错的不报，不确定的写明。

数人头要准：写“三位都说”之前，回头对一遍是哪三位。最容易错的是把一位的话算成两位，或把没读到铺垫的读者算进接住表。

## 七、写笔记

写进 `notes/fresh-read.md`，一轮一节，标日期和范围。上一轮已经办完的部分直接删去，历史在 git，不加“已办”“作废”注记。读者用“甲、乙”（全读两位）和段落（如“91–95 那位”）指称。

每节依次写：

1. **怎么读的**：几位、谁读哪几回、给了什么不给什么、读的是哪一版；局限照写：读者都是模型，同写稿的是一个模型，口味可能相近，熟前八十回，不算普通读者；全读一口气二十来回，后几回可能读粗。
2. **不说破的几处，接住没有**：一张表，列“处 ｜ 铺垫→落点 ｜ 本意 ｜ 甲 ｜ 乙 ｜ 结论”。
3. **两位以上各自说到的**：按轻重排，最大的一条放最前，并说清它同第 2 节哪几处没接住是不是同一个缺口。
4. **可能前文交代过**：分段读者说没看懂的，对一遍全读两位读到那里懂没懂；懂了的删去，剩下的照记。
5. **读者最喜欢的（改时别碰）**：改稿时最容易误伤的就是这些。
6. **核过的硬伤（正文未改）。**
7. **留给作者定的**：照自顶向下，先列牵动骨架的（注明骨架哪一条），再列只动卡和正文的；每条给可选做法，不替作者定。

## 八、回报

回复用户时先说最大的一两条，再说接住和没接住的、核过的硬伤，最后一句建议先做哪一件。照 AGENTS.md 报告改了哪些回（冷读本身是 0 回）、代码净增减多少行。笔记不提交，等用户说。
